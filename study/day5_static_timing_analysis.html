01
Foundation
What STA Does & Why It Beats Simulation

Static Timing Analysis is the process of mathematically verifying that all timing paths in a design meet their setup and hold requirements — without running a single simulation vector. It is the cornerstone of every digital chip's verification sign-off, and the primary tool PD engineers use to judge the quality of their work at every stage.

STA vs Dynamic Simulation

PropertyDynamic SimulationStatic Timing Analysis
CoverageOnly paths exercised by test vectors — typically <5% of all pathsEvery timing path in the design — 100% coverage by definition
SpeedHours to days for large designsMinutes to hours for millions of paths
Input requiredTest vectors (stimulus) must be writtenNo vectors needed — only constraints (SDC)
What it findsFunctional bugs AND timing — but only on exercised pathsAll timing violations, including those never stimulated
False pathsNaturally avoided if vectors don't exercise themMust be explicitly declared in SDC with set_false_path
Used atRTL verification, gate-level verificationSynthesis, post-placement, post-CTS, post-route, final signoff
⚠ The Fundamental Guarantee of STA

If STA reports zero timing violations (WNS ≥ 0, TNS = 0) at all required PVT corners, and all constraints are correctly written, then the chip will meet its timing specification on silicon — regardless of what data patterns appear. This is the mathematical certainty that makes STA so powerful. A chip with simulation-passing but STA-failing timing will fail in the field.

What STA Actually Computes

STA traverses the entire netlist graph and computes, for every possible timing path:

  1. Arrival time at every node — how long it takes for a signal to propagate from its source to that point
  2. Required time at every endpoint — the latest time data must arrive to satisfy setup (or earliest for hold)
  3. Slack = Required − Arrival for each endpoint — negative slack is a violation

The tool does this simultaneously for all paths, using the timing arcs from Liberty files and wire parasitics from SPEF (post-route), giving a complete picture of the design's timing health in a single pass.

Timing Paths — Anatomy & All Four Types

Every timing path has a startpoint, an endpoint, and logic between them. Understanding path anatomy at the granular level lets you read any timing report instantly and know exactly where to apply fixes.

The Register-to-Register Path — Full Anatomy

COMPLETE REG-TO-REG TIMING PATH ANATOMY LAUNCH SIDE CAPTURE SIDE ──────────── ──────────── CLK source CLK source │ │ ▼ source latency (Tsl_launch) ▼ source latency (Tsl_capture) CLK at launch FF pin CLK at capture FF pin │ │ ▼ Tcq (clock-to-Q delay) │ Launch FF Q output │ │ │ ▼ Gate 1 propagation (t1) │ ▼ Gate 2 propagation (t2) │ ▼ Gate 3 propagation (t3) │ ▼ Net delay (Tnet) — wire RC parasitic │ │ │ ▼ arrives at Capture FF D pin │ Capture FF D input ←── must arrive by ──→ Capture CLK edge − Tsetup − Tuncertainty SETUP SLACK = Required Arrival − Actual Arrival = (T_period + Tsl_capture − Tsetup − Tuncert) − (Tsl_launch + Tcq + Tlogic + Tnet) Every line in the timing report corresponds to one segment of this path.

Understanding Timing Arc Direction: Unateness

Every timing arc in the Liberty file has a sense — how input transitions propagate to the output. STA uses this to determine whether a rising or falling edge propagates through each gate:

Timing SenseMeaningExample Gates
Positive_unateInput rise → Output rise. Monotonically increasing.BUF, AND, OR, NAND (at inverted output)
Negative_unateInput rise → Output fall. Monotonically decreasing.INV, NAND, NOR (at true output)
Non_unateInput rise → Output can rise OR fall depending on other inputsXOR, XNOR, MUX
📌 Why Unateness Matters in STA

STA must track whether each node in a path is transitioning HIGH or LOW to look up the correct rise or fall delay from the Liberty table. A chain of inverters alternates between rise and fall arcs. XOR gates (non-unate) require STA to compute both rise and fall delays and take the worst case. This is why timing paths show "rise" and "fall" annotations on each arc.

⚠ The Most Important Number: WNS vs TNS

WNS (Worst Negative Slack) tells you the severity of the worst single violation — how much timing improvement is needed on the hardest path. TNS (Total Negative Slack) tells you the total scope of work — how many path-picoseconds of violation exist across the entire design. A design with WNS=−5ps and TNS=−50ps is almost done (a few small violations). A design with WNS=−5ps and TNS=−50,000ps has thousands of paths all slightly failing — much more work to fix.

Multi-Corner Analysis & MMMC

Real chips must work correctly across a range of process, voltage, and temperature (PVT) conditions. A chip that passes timing at the nominal corner but fails at the slow corner will fail in the field when the temperature is high or the supply voltage dips. MMMC — Multi-Mode Multi-Corner — is the methodology that ensures correctness across all conditions simultaneously.

Why Multiple Corners Are Required

Silicon transistors are manufactured with inherent variability. Two identical chips from the same wafer may have Vt differing by ±50mV. Environmental conditions (temperature, voltage) further shift performance. The intersection of all these variations produces corners:

PVT CORNER SPACE Process: Slow ←──────────────────────────→ Fast Voltage: Low ←──────────────────────────→ High Temp: Hot ←──────────────────────────→ Cold Worst Setup Corner: SS + Low VDD + Hot Temp → Everything slow → data arrives late → setup hardest to meet → Named: ss_0.9v_125c or "slow corner" Worst Hold Corner: FF + High VDD + Cold Temp → Everything fast → data arrives too early → hold hardest to meet → Named: ff_1.1v_n40c or "fast corner" Typical Corner: TT + Nom VDD + Room Temp → Average conditions → used for power analysis and exploration → Named: tt_1.0v_25c Special Corners: sf_1.0v_25c → Slow NMOS, Fast PMOS → worst for some paths fs_1.0v_25c → Fast NMOS, Slow PMOS → worst for complementary paths

MMMC — Analyzing All Corners Simultaneously

MMMC runs STA across all corners in a single session, ensuring no corner is neglected. Modern PnR tools (ICC2, Innovus) and signoff STA tools (PrimeTime) all support MMMC natively:

MMMC / Tcl
## MMMC Setup in PrimeTime / OpenSTA # 1. 📌 PD Engineer MMMC Workflow

At the start of a PD project, the timing team provides an MMMC configuration file defining all corners and modes. PD engineers load this configuration into ICC2 or Innovus at the beginning of the flow. All placement, CTS, and routing optimizations run simultaneously across all active corners. Fixing timing in one corner must not break another — the tool automatically checks all corners after every optimization step. At signoff, PrimeTime re-runs all corners one final time with extracted SPEF.

On-Chip Variation (OCV) & Timing Derating

Even within a single chip, different regions experience different local conditions. A transistor in the center of the die sees different temperature, IR drop, and process variations than one at the corner. This intra-die variation is called On-Chip Variation (OCV), and ignoring it leads to silicon failures even when global-corner STA passes.

Sources of On-Chip Variation

  • Process gradients — photolithography has slight focus and dose variations across the wafer → transistor sizes vary by 2–5% spatially
  • Thermal gradients — power-hungry blocks (CPU core, GPU) heat their neighbors by 10–20°C above ambient
  • IR drop — voltage drops across the power grid resistance mean far cells see lower VDD than cells near pads
  • Aging — Hot Carrier Injection (HCI) and Bias Temperature Instability (BTI) degrade transistors over time → cells slow down by 5–15% over chip lifetime

OCV Derating — The Conservative Fix

The simplest OCV modeling approach applies a derating factor to timing arcs: launch path delays are made pessimistically late, and capture path delays are made pessimistically early, modeling the worst-case OCV scenario:

OCV Derating Applied to Timing
For Setup analysis (worst case: data late, clock early): T_launch_derated = T_launch_nominal × (1 + derate_data) ← make data slower T_capture_derated= T_capture_nominal × (1 − derate_clock) ← make clock faster For Hold analysis (worst case: data early, clock late): T_launch_derated = T_launch_nominal × (1 − derate_data) ← make data faster T_capture_derated= T_capture_nominal × (1 + derate_clock) ← make clock slower Typical derate values: OCV (basic): 5–10% on cell delays AOCV: varies by logic depth (deeper paths → less derate) POCVM/SOCV: statistical model — most accurate at 5nm and below

Clock Analysis
Clock Uncertainty, Jitter & Skew

The clock is not a perfect square wave. It has variability in its period, phase, and edge position. STA models this variability through the clock uncertainty budget, which is subtracted from the available timing margin. Understanding each component helps you write accurate SDC and diagnose timing problems correctly.

Clock Uncertainty Budget — All Components

Clock Uncertainty Decomposition
T_uncertainty = T_jitter + T_skew + T_margin Component breakdown: T_jitter (Clock Source Jitter): = Cycle-to-cycle variation in clock period from PLL/oscillator = ±20–100ps for typical PLLs Modeled in STA as: σ_jitter × target_sigma (e.g., 3σ for 99.7% yield) Applied to: both setup and hold (adds uncertainty to both) T_skew (Pre-CTS Estimate): = Expected clock arrival time difference between launch and capture FF Before CTS: tool uses an estimate (e.g., 200ps) After CTS: tool uses ACTUAL propagated clock delays → skew is real Applied to: depends on sign — positive skew helps setup, hurts hold T_margin (Guardband): = Extra safety margin for unmodeled effects: crosstalk on clock nets, voltage noise, process corners beyond analyzed range = 50–100ps typical Typical total uncertainty values: Pre-CTS: set_clock_uncertainty -setup 0.20 (200ps) Pre-CTS: set_clock_uncertainty -hold 0.05 (50ps) Post-CTS: set_clock_uncertainty -setup 0.10 (100ps — skew now real) Post-CTS: set_clock_uncertainty -hold 0.05 (50ps)

Jitter Types

Jitter TypeDefinitionEffect on Timing
Cycle-to-Cycle JitterVariation in period between adjacent cycles. Period_n vs Period_(n+1)Affects setup: data has less time if the previous cycle was shorter
Period JitterDeviation of any clock period from the ideal periodWorst case for timing — PLL specs define max period jitter
Long-Term JitterAccumulated phase error over many cyclesCritical for high-speed serial interfaces (PCIe, DDR)
Duty Cycle DistortionDeviation of HIGH pulse width from 50%Affects timing in double-data-rate (DDR) systems

Clock Skew — Positive vs Negative

CLOCK SKEW EFFECTS Positive Skew (capture gets clock LATER than launch): Launch FF ──[clock]──→ at t=0 Capture FF ──[clock]──→ at t=+100ps (skew = +100ps) Setup check: capture edge is at (T_period + 100ps) → Setup HELPED: 100ps more time for data to travel Hold check: capture edge is at (0 + 100ps) → Hold HURT: data must stay stable 100ps longer after launch CK Negative Skew (capture gets clock EARLIER than launch): Launch FF ──[clock]──→ at t=0 Capture FF ──[clock]──→ at t=−100ps (skew = −100ps) Setup check: capture edge is at (T_period − 100ps) → Setup HURT: 100ps less time for data to travel Hold check: capture edge is at (0 − 100ps) → Hold HELPED: data can change 100ps sooner USEFUL SKEW: Deliberately creating positive skew on critical paths → allows more time for data on setup-critical paths → PD tool does this automatically via "useful skew optimization"

Fixing Timing Violations — The Complete Toolkit

Timing closure is the iterative process of eliminating all timing violations across all corners and modes. It is the most demanding part of the PD job and where experience separates good engineers from great ones. This section gives you the complete mental model for systematic timing closure.

Setup Violation Fixes — Ordered by Impact

Fix TechniqueMechanismImpactCost
1. Cell upsizingReplace NAND2X1 → NAND2X2/X4. Higher drive strength → faster Q transition (less Tcq and less output slew for fan-out)High — 50–200ps improvement per cellArea, power
2. Vt swapping (HVT→SVT→LVT)Lower Vt → faster switching. Same function, different speed/leakage trade-offHigh — 20–100ps per swapLeakage power
3. Buffer/repeater insertionBreak long net into segments → each segment has lower C_load → faster transitionsMedium — reduces net delay by restoring slewArea, power, routing resources
4. Placement improvementMove critical-path cells closer together → shorter wires → less T_netMedium — each mm of wire ≈ 50–100ps RC delayMay cause congestion elsewhere
5. Logic restructuringReduce number of logic levels on critical path (gate reordering, factoring)High but complex — reduces T_logic fundamentallyNetlist changes — requires synthesis re-run
6. Useful skewDeliberately delay capture clock relative to launch → more time for dataMedium — can recover 50–200ps on targeted pathsMay create hold violations on other paths
7. Reroute critical netsRoute on lower-resistance metal layer (M5 vs M2) → less RC delayLow-medium — 20–50ps improvement on long netsRouting resources on upper metals

Hold Violation Fixes

⚠ The Immutable Rule of Hold Fixing

NEVER modify the clock path to fix a hold violation. Always add delay to the DATA path only. Adding clock delay to the capture FF seems logical (make clock arrive later = more time for hold) but it creates new hold violations on every other path that captures from that clock node — a cascade failure. The correct fix is always: insert delay cells (DLYND, BUFD, INV+INV pairs) directly on the data path between the launch and capture flip-flops.

Fix TechniqueMechanismNotes
Delay cell insertionInsert dedicated delay cells (DLYND1, DLYND2) on data path — adds fixed ps of delayCleanest fix. Many libraries include delay-tuned cells specifically for hold fixing.
Inverter pair insertionInsert INV+INV on data path — logical no-op but adds ~80–120ps delayCommon quick fix during ECO. Less elegant but effective.
Cell downsizingReplace X4/X8 cells with X1/X2 on the data path — smaller cells drive more slowlyUse only if the path has large positive setup slack — must check setup isn't broken
Vt swap (LVT→SVT→HVT)Higher Vt cells switch more slowly → data arrives later at capture DEffective but reduces drive strength — verify setup timing afterward
Route on higher resistance layerRoute hold-violating net on thin metal (M1/M2) instead of wide metal → more RC delayUsed for fine-tuning hold margin. Router ECO can target specific nets.

Systematic Timing Closure Methodology

TIMING CLOSURE LOOP — PD ENGINEER'S WORKFLOW 1. Run STA (PrimeTime / OpenSTA) ↓ 2. Check: WNS ≥ 0? TNS = 0? Both corners? ↓ ├── YES → Timing CLEAN → proceed to next PD stage │ └── NO → Timing violations exist ↓ 3. Sort failing paths by slack (most negative first) ↓ 4. Identify violation type: Setup? → analyze critical path → upsize/swap cells → reroute Hold? → identify short path → insert delay buffers on DATA path ↓ 5. Apply ECO (Engineering Change Order) - Cell size change - Buffer insertion / deletion - Net rerouting ↓ 6. Re-run STA on modified design ↓ 7. Verify fix didn't create new violations elsewhere ↓ Loop back to step 2 until clean NOTE: Each ECO round typically fixes the worst 10-20% of violations. A design with 500 violations typically requires 5-10 ECO iterations.

Summary
Day 5 — What to Remember Forever
STA Power
100% path coverage. No vectors needed. Runs in minutes. The only timing method that can guarantee silicon correctness.
Slack Formula
Setup: Required − Arrival = (T_period − Tsetup − Tunc) − (Tcq + Tlogic + Tnet). Must be ≥ 0.
WNS vs TNS
WNS = single worst path. TNS = total violation sum. Both must be 0 at tapeout. TNS reveals scope of work.
check_timing
Always run first. Zero unconstrained paths mandatory before trusting any timing number. One unconstrained path = one potential silicon failure.
MMMC Corners
Setup → SS corner (slow, hot, low V). Hold → FF corner (fast, cold, high V). Both simultaneously via MMMC. Never TT-only signoff.
OCV Derating
Spatial intra-die variation. Launch path derated slow, capture path derated fast (for setup). AOCV: longer paths get less derate (statistical averaging).
Clock Uncertainty
= Jitter + estimated skew + guardband. Pre-CTS: 200ps setup. Post-CTS: 100ps setup (skew now real from propagated clock).
Hold Fix Rule
NEVER touch clock path for hold. ALWAYS add delay to DATA path. Delay buffers, INV pairs, cell downsizing, HVT swap — all on data path only.
Day 5 Complete STA Formula Reference
SETUP SLACK = (T_period + Tsl_cap − Tsetup − Tuncertainty) − (Tsl_launch + Tcq + Tlogic + Tnet) HOLD SLACK = (Tcq + Tlogic + Tnet) − (Thold + Tuncertainty + Tskew_cap) With OCV derating (setup): T_launch_eff = T_nominal × (1 + derate) ← data path: pessimistically slow T_capture_eff= T_nominal × (1 − derate) ← clock path: pessimistically fast Fix priority order: Setup: cell upsize → LVT swap → buffer insertion → placement → useful skew Hold: delay buffer → INV pair → cell downsize → HVT swap ← DATA PATH ONLY

01 · Power
Dynamic Power — The V² Law

Power is the dominant design constraint in modern SoCs. Mobile phones, AI chips, and data-center processors are all power-limited — not transistor-limited. As a PD engineer, you will optimize for power at every stage: floorplan, placement, CTS, routing, and signoff. This section gives you the physics you need.

The Three Components of Total Power

Total Power Budget
P_total = P_dynamic + P_short_circuit + P_leakage P_dynamic ≈ 60–80% of total (dominant in older nodes: 180nm–65nm) P_short_circuit ≈ 5–10% of total (brief PMOS+NMOS overlap during switching) P_leakage ≈ 20–40% of total (dominant in advanced nodes: 28nm–3nm)

Dynamic Power — Deep Dive

Every time a node in your design switches from 0→1 or 1→0, it charges or discharges the capacitance on that wire. That charging takes energy from the power supply. The energy spent per switching event is what we call dynamic power.

Dynamic Power Formula
P_dynamic = α × C_L × V²_DD × f α = Activity factor (0 → 1.0) Probability that a node switches each clock cycle Clock net: α ≈ 1.0 | data bus: α ≈ 0.1–0.3 | rare signals: α ≈ 0.01 C_L = Load capacitance at output node = Wire capacitance + input capacitances of fan-out gates Unit: fF or pF | Typical: 10fF – 500fF per net V_DD = Supply voltage ← THE MOST POWERFUL LEVER (appears squared!) Reducing VDD 20% → P_dynamic drops 36% Reducing VDD 30% → P_dynamic drops 51% f = Clock frequency Linear relationship — 2× frequency → 2× dynamic power
🧠 Blueprint Analogy

Think of dynamic power as filling and draining a water tank every clock cycle. The tank size is C_L (capacitance). The water pressure is V_DD (voltage). The fill/drain rate is frequency f. The activity factor α is how often the pump actually runs. If you lower the pressure (VDD) by 30%, you spend only 49% as much energy per fill — because energy = ½·C·V². That squared relationship is why voltage scaling is so powerful.

Understanding Activity Factor (α) in PD

The activity factor is what makes power analysis complex in real chips. Different nets switch at vastly different rates:

Net TypeTypical αWhyPD Action
Clock tree1.0Toggles every single cycle by definitionClock gating — most impactful power fix
Arithmetic data (ALU)0.3–0.5Operands change frequently during computationOperand isolation, power gating
Control signals0.05–0.15Change only when mode/state changesMinimal concern
Status/flag bits0.01–0.05Rarely changeNegligible dynamic power
Glitch nodesup to 2.0!Multiple spurious transitions before settlingBalance logic paths, add buffers to eliminate glitches
⚡ Critical PD Insight — Glitching

Glitches occur when paths through combinational logic have different delays — faster paths arrive at the output and cause spurious transitions before the slower paths settle. Glitches can give α > 1.0, consuming MORE power than expected. PD engineers fix glitches by balancing path delays through buffer insertion or netlist restructuring. This is checked during post-route power analysis.

Short-Circuit Power

During a signal transition, there is a brief moment when both PMOS (pull-up) and NMOS (pull-down) transistors are partially ON simultaneously — creating a direct current path from VDD to GND. This is short-circuit (or crowbar) current.

  • Duration: determined by input rise/fall time (slew rate)
  • Faster input transitions → shorter overlap → less short-circuit power
  • Very slow slews → long overlap → significant power and heat
  • PD fix: max_transition constraints in SDC prevent excessively slow slews; tools insert buffers to restore signal integrity

Static Leakage Power

Leakage power is what a chip consumes even when it is completely idle — no clock, no switching. At 28nm and below, leakage can equal or exceed dynamic power. Understanding leakage lets you make smart PD decisions about cell selection and placement.

Three Sources of Leakage

Leakage TypeMechanismDominanceScales With Node?
Subthreshold LeakageCurrent flows even when VGS < Vt — exponential in (VGS−Vt). Dominant leakage source.60–80% of total leakageWorsens severely at advanced nodes
Gate Oxide LeakageElectrons tunnel through ultra-thin gate oxide (<3nm thick) directly from gate to channel10–20% at 45nm+Worsens with thinner oxide (FinFET uses high-k to mitigate)
Junction LeakageReverse-biased p-n junction leakage between drain/source and bulk5–10%Less critical at modern nodes

Subthreshold Leakage — The Key Equation

Subthreshold Leakage Current
I_sub = I₀ × exp((VGS − Vt) / (n × Vth)) I₀ = process-dependent current at VGS = Vt VGS = gate-to-source voltage (= 0 when transistor is "off") Vt = threshold voltage n = subthreshold swing factor (1.0–1.5 for bulk CMOS) Vth = thermal voltage = kT/q ≈ 26mV at room temperature KEY INSIGHT: Every 100mV increase in Vt → 10× reduction in I_sub → This is exactly why High-Vt (HVT) cells leak far less!
🧠 Analogy

Subthreshold leakage is like a leaky faucet that you can never fully close. Higher Vt is like a tighter washer — much less drip. But a tighter washer also requires more force to turn the tap on (higher gate voltage needed = slower switching). This is the fundamental speed-power tradeoff in every library cell.

Multi-Vt Strategy in PD

Standard cell libraries provide the same logic function (e.g., NAND2) in multiple threshold voltage variants. The PD engineer's job is to choose the right one for each cell in the design:

Cell TypeThreshold VoltageSpeedLeakageUse Case
LVT (Low Vt)~0.2–0.3VFastestHighest (~10–100×)Critical timing paths only — WNS is negative
SVT (Standard Vt)~0.35–0.45VMediumMedium (baseline)Default for most logic — balanced design
HVT (High Vt)~0.5–0.6VSlowestLowest (~10–100× less)Non-critical paths — maximum power saving
ULVT (Ultra-Low Vt)<0.2VFastestExtremely HighExtreme performance paths only
📌 PD Engineer's Multi-Vt Workflow

After routing, run post-route STA. All paths with setup slack > 300ps are non-critical — swap those cells from SVT to HVT. This can reduce total leakage by 20–40% with zero timing impact. Then re-run STA to verify. This "Vt migration" ECO is a standard step in any PD signoff flow.

03 · Power
Power Reduction Techniques

Real PD engineers use a toolkit of techniques across the entire design flow to meet power budgets. You will implement all of these by Phase 6 of your training.

Clock Gating — The Single Most Impactful Technique

Since the clock tree has α=1.0 and drives every flip-flop in the design, it consumes 20–40% of total chip power. Clock gating turns off the clock to idle blocks — setting their effective α to 0.

BEFORE CLOCK GATING (wasteful) CLK ──────────────────────── FF_1 │ ↑ switching every cycle even if D doesn't change ├──────────────── FF_2 ← wasting power └──────────────── FF_N AFTER CLOCK GATING (efficient) CLK ───[ICG Cell]──────────── FF_1 │ ↑ ↑ clock only when ENABLE is HIGH │ ENABLE (data is actually changing) └──────────────────── FF_2 ICG = Integrated Clock Gate = latch + AND gate in one cell The latch prevents glitches on the gated clock output Power saving: up to 30-40% reduction in clock network power
📌 PD Engineer's Role in Clock Gating

RTL designers insert clock gating logic. Synthesis tools map it to ICG cells. PD engineers must: (1) ensure ICG cells are placed close to the FF clusters they gate, (2) check that CTS handles gated clocks correctly — ICG outputs are treated as clock roots, (3) verify that clock gating doesn't create new hold violations on ungated paths.

Power Gating — Shutting Off Entire Blocks

When a circuit block is completely idle (e.g., a GPU shader unit when no graphics work is queued), we can cut its power supply entirely using a power switch (header/footer cell):

VDD (always on) │ [HEADER SWITCH] ← PMOS transistor, large W/L to minimize R_on │ VDD_sw (switched domain) ────┬── cells in power-gated block └── (leakage = 0 when switch is OFF) Power gating requires: 1. Isolation cells — clamp outputs to known level when block is off 2. State retention FFs — save FF state before power off, restore after 3. Wakeup sequencing — ramp power, release reset, restore state Defined in UPF (Unified Power Format) files — you implement this in Phase 6

Voltage Scaling and Multi-Voltage Domains

Since P_dynamic ∝ V², running a block at lower VDD is the most powerful single power reduction. Modern SoCs have multiple voltage domains:

DomainVoltageWhy This VoltagePD Requirement
High-performance core1.0V–1.1VMaximum frequency neededStandard PD flow
Standard logic0.9VBalanced perf/powerStandard cells optimized for this VDD
Memory (SRAM)0.8V–0.9VOptimized read marginSeparate PDN, level shifters at boundary
Always-on domain0.7V–0.8VMinimum needed to hold stateLevel shifters at every domain crossing
⚡ PD Impact of Multi-Voltage

Every boundary between voltage domains requires Level Shifter cells (to safely cross from low to high VDD or vice versa) and Isolation cells (to clamp outputs to a known value when the source domain is powered off). PD engineers must place these cells exactly at the domain boundary in the floorplan, route their supply connections carefully, and ensure STA is run separately for each domain corner.

04 · Flow
Full RTL-to-GDSII Pipeline

Every chip manufactured in the world goes through this pipeline. As a PD engineer, you own the back half — from synthesis handoff to GDSII tapeout. Understanding every stage — even those you don't own — makes you a far better PD engineer because you understand the inputs you receive and the constraints they carry.

1. System Specification ARCH TEAM
Define chip architecture: frequency targets, power budget, area constraints, features, interfaces. Output: architecture spec document, performance targets.
2. RTL Design RTL DESIGN TEAM
Write synthesizable Verilog/VHDL. Functional verification via simulation and formal. Output: verified .v RTL files.
design.vconstraints.xdctestbench.v
3. Logic Synthesis SYNTHESIS TEAM
Map RTL to standard cell gate-level netlist using Synopsys DC or Cadence Genus. Optimize for timing, area, power per SDC constraints. Output: gate netlist + timing reports.
netlist.vconstraints.sdctiming.rpt
4. Floorplanning YOUR JOB — PD
Define die/core area, utilization, place macros (memories, IPs), define IO placement, insert power grid (rings + straps), add tap/end-cap cells. First physical view of the chip.
floorplan.defpower.deficc2_fp.tcl
5. Placement YOUR JOB — PD
Place all standard cells — global placement (minimize wirelength) then legalization (no overlaps) then detailed placement (timing optimization). Pre-CTS timing analysis.
placement.defcongestion.rptpre_cts_timing.rpt
6. Clock Tree Synthesis (CTS) YOUR JOB — PD
Build balanced clock distribution network. Control skew, latency, insertion delay. Fix setup/hold violations introduced by real clock delays.
cts.defclock_tree.rptpost_cts_timing.rpt
7. Routing YOUR JOB — PD
Global routing assigns nets to routing regions. Detailed routing assigns exact tracks, layers, vias. Fix DRC violations. Extract parasitics (SPEF).
routed.defdesign.spefdrc.rpt
8. Signoff Verification YOUR JOB — PD
DRC (design rules), LVS (layout vs schematic), STA with parasitics (post-route timing), IR drop (power grid integrity), EM (electromigration), antenna checks.
drc_clean.rptlvs_clean.rptfinal_sta.rpt
9. GDSII Tapeout BACK TO FAB
Export final GDSII layout. Submit to foundry (TSMC, Samsung, GlobalFoundries). Fabrication: 4–12 weeks. Then packaging, testing, ship.
final.gdslef_abstract.lef
10. Silicon & Validation VALIDATION TEAM
First silicon characterized. Speed, power, functionality tested at wafer level. Any failures → post-silicon debug → ECO → re-spin (expensive!).
✅ Your Role Summary

Steps 4 through 8 are Physical Design — that is your domain. You receive the gate-level netlist from synthesis and deliver a verified GDSII to the foundry. Every day at work you will be running one of these stages, reading reports from them, or fixing violations they reveal. The entire chip's physical existence depends on your work.

Key File Formats in Physical Design

PD tools communicate through a set of standard file formats. You will read, write, and debug these files daily. Knowing what each contains and why it exists is essential.

FormatExtensionContainsUsed By
Verilog Netlist.vGate-level netlist — instantiates standard cells and connects them. Your starting point in PD.PnR tools, STA, LVS
SDC.sdcSynopsys Design Constraints — clock definitions, input/output delays, exceptions. Drives all timing analysis.Synthesis, PnR, STA
LEF.lefLibrary Exchange Format — abstract physical view of cells: pin locations, dimensions, obstruction layers. NOT transistor details.PnR tools (placement, routing)
Liberty (.lib).lib / .dbTiming/power model for each cell: setup/hold tables, Tcq, pin capacitances, leakage. The timing bible.Synthesis, STA, PnR

📌 The PD File Flow

At the start of your PD run you receive: .v (netlist) + .sdc (constraints) + .lef (cell abstracts) + .lib (timing models). You produce: .def files at each stage, culminating in a final .gds. After routing you extract .spef parasitics and feed them back into STA. This file handoff chain is your daily workflow.

06 · Verilog
Verilog Basics Every PD Engineer Must Know

PD engineers are NOT expected to write RTL from scratch — that is the RTL designer's job. However, you must be able to read and understand Verilog because: you debug netlists, you read gate-level Verilog from synthesis, you write Tcl scripts that reference cell and port names, and you communicate with RTL designers about timing paths that reference specific registers by their hierarchical names.

Module and Port Declaration

Verilog
module alu_block ( input wire clk, // clock — this drives all FFs inside input wire rst_n, // active-low reset input wire [7:0] data_in, // 8-bit input bus input wire [1:0] op_sel, // 2-bit operation select output reg [7:0] result, // 8-bit registered output output wire valid // combinational valid flag ); // ... module body here ... endmodule // PD NOTE: Each module = one hierarchical block in your design // In timing reports you will see paths like: alu_block/result_reg[3]/Q // That means: module alu_block, register "result", bit 3, output Q

Combinational Logic — assign Statement

Verilog
wire [7:0] sum; wire carry_out; wire overflow; // Continuous assignment — combinational logic assign {carry_out, sum} = data_in + operand_b; assign overflow = carry_out ^ sum[7]; assign valid = (op_sel != 2'b11); // valid when not idle // PD NOTE: Every assign statement synthesizes to combinational gates // These form the logic cones BETWEEN flip-flops in your timing paths // The delay through these cones = T_logic in your STA equations

Sequential Logic — always Block (The Most Important Pattern)

Verilog
// Synchronous reset D Flip-Flop — THE standard pattern always @(posedge clk or negedge rst_n) begin if (!rst_n) begin result <= 8'h00; // async reset — clear to 0 end else begin case (op_sel) 2'b00: result <= data_in; // PASS THROUGH 2'b01: result <= data_in + 8'd1; // INCREMENT 2'b10: result <= data_in << 1; // LEFT SHIFT default: result <= result; // HOLD (no change) endcase end end // PD BREAKDOWN: // "always @(posedge clk)" → synthesizes to D Flip-Flops clocked by clk // "result <= ..." → non-blocking assignment = registered output // "if (!rst_n)" → async reset: synthesis creates DFFRX cells // The case statement → combinational mux in front of the FF's D input // In STA: result_reg[7:0] are 8 DFFs, each with a timing path from // op_sel, data_in through the mux logic to result_reg[N]/D

Module Instantiation — Building Hierarchy

Verilog
module top_chip ( input wire clk, rst_n, input wire [7:0] top_in, output wire [7:0] top_out ); wire [7:0] alu_result; wire alu_valid; // Instantiate the ALU block — named instantiation (preferred) alu_block u_alu ( // u_alu = instance name .clk (clk), .rst_n (rst_n), .data_in (top_in), .op_sel (2'b01), // hardwired to INCREMENT mode .result (alu_result), .valid (alu_valid) ); assign top_out = alu_valid ? alu_result : 8'h00; endmodule // PD HIERARCHY NOTE: // In a timing report, paths reference the FULL hierarchical path: // top_chip/u_alu/result_reg[3]/CK → top_chip/u_alu/result_reg[3]/Q // In ICC2/Innovus, you reference cells by hierarchy: // get_cells top_chip/u_alu/result_reg* → all 8 bits of result register
07 · Verilog
Synthesizable vs Non-Synthesizable RTL

Not all Verilog is equal. Synthesis tools only accept a subset of Verilog — the synthesizable subset. RTL that uses non-synthesizable constructs will fail during synthesis and you will never get a netlist to work with. As a PD engineer, recognizing the difference helps you understand why certain design patterns exist and why synthesis engineers write code the way they do.

ConstructSynthesizable?Synthesizes ToNotes
assign a = b & c;✓ YESAND2 gateCombinational logic
always @(posedge clk)✓ YESD Flip-FlopsStandard register pattern
if / else / case✓ YESMUX treesCombinational or sequential
+, -, <<, >>✓ YESAdder, shifter logicSynthesizable arithmetic
initial begin ... end✗ NOSimulation onlyUsed in testbenches, ignored by synthesis
#10 a = b;✗ NOSimulation delaySynthesis ignores all # delays
$display, $monitor✗ NOSimulation outputSystem tasks — not in hardware
always @(*) with loops⚠ PARTIALComplex combinationalDepends on loop bounds — must be constant
real, time data types✗ NON/AFloating-point unsupported in synthesis
📌 Common RTL Coding Style Issues PD Engineers Encounter

Inferred latches — when a signal is not assigned in all branches of a combinational always block, synthesis infers a latch. Latches cause headaches in STA (level-sensitive timing). PD engineers see this as unexplained latch cells in the netlist. Multiple drivers — a net driven by two sources creates shorts in layout; synthesis throws an error. Incomplete sensitivity list — in older Verilog (pre-2001), missing signals in @() cause simulation-synthesis mismatch — a nightmare to debug in silicon.

08 · Verilog
Reading a Gate-Level Netlist

After synthesis, your design exists as a gate-level netlist — a Verilog file where every logic operation is expressed as an instantiation of a real standard cell. This is the file you will read, debug, and modify (via ECO) throughout your PD career. You must be able to decode it fluently.

Annotated Gate-Level Netlist Example

Gate-Level Netlist
// ─── Synthesized by Synopsys DC from counter.v ─── module counter ( clk, rst_n, count ); input clk, rst_n; output [3:0] count; // ── Internal wires (synthesized node names) ── wire n1, n2, n3, n4, n5; wire [3:0] count_next; // ── Combinational Logic (the +1 increment) ── INVX1 U1 (.A(count[0]), .Y(count_next[0])); // bit0 inverts XOR2X1 U2 (.A(count[1]), .B(count[0]), .Y(count_next[1])); // bit1 AND2X1 U3 (.A(count[1]), .B(count[0]), .Y(n1)); // carry XOR2X1 U4 (.A(count[2]), .B(n1), .Y(count_next[2])); // bit2 AND2X1 U5 (.A(count[2]), .B(n1), .Y(n2)); // carry XOR2X1 U6 (.A(count[3]), .B(n2), .Y(count_next[3])); // bit3 // ── Sequential Elements (the 4 flip-flops) ── // DFFRHQX1 = D Flip-Flop with async Reset, H drive, Q output, X1 strength DFFRHQX1 count_reg_0 (.D(count_next[0]), .CK(clk), .RN(rst_n), .Q(count[0])); DFFRHQX1 count_reg_1 (.D(count_next[1]), .CK(clk), .RN(rst_n), .Q(count[1])); DFFRHQX1 count_reg_2 (.D(count_next[2]), .CK(clk), .RN(rst_n), .Q(count[2])); DFFRHQX1 count_reg_3 (.D(count_next[3]), .CK(clk), .RN(rst_n), .Q(count[3])); endmodule // ── HOW TO READ THIS AS A PD ENGINEER ────────────────────── // Cell name: DFFRHQX1 → from the standard cell library // DFF = D Flip-Flop // R = has Reset pin // H = high drive (some libs use drive strength here) // Q = Q output available // X1 = drive strength 1 (smallest, lowest power) // // Timing path for count[3]: // count_reg_2/Q → U5/A (AND2) → U5/Y → U6/B (XOR) → U6/Y → count_reg_3/D // This is the CRITICAL PATH — longest carry chain in the ripple adder // // ECO insight: if count_reg_3 has setup violation, you upsize U5 or U6 // from X1 to X2 to reduce their propagation delay
✅ What You Just Learned to Read

Every day as a PD engineer you will look at netlists like this to understand which cells are on the critical path, why a timing violation exists, which cell to upsize in an ECO, and how to interpret what a synthesis tool produced. This skill takes practice — but now you have the vocabulary to start.
